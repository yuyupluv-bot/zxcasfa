# V179 — защита бота от зависаний и повторных ошибок VK

## Подтверждённая проблема

В присланном журнале повторялось закрытие пассажирской оценки заявки 10335:
VK возвращал 9 (Flood control) и 901 (нет разрешения на сообщения), а общий
планировщик повторял неудачный callback через 15 секунд. В том же журнале
38 раз встречались недействительные Firebase-токены. Это подтверждённые
дефекты обработки ошибок. Точная причина полного зависания до ручного
перезапуска по журналу не установлена; утверждать, что это был именно таймер,
нельзя.

## Изменения

- Срок оценки по-прежнему 12 часов. Истечение сохраняется в БД, указатель
  открытой оценки снимается; редактирование старой карточки выполняется отдельно.
  Поздняя оценка отклоняется существующими проверками открытого prompt.
- Сетевое редактирование отложенных карточек вынесено из транзакции БД.
- При 9/29/901/911 редактирование не перебирает дополнительные ID/параметры.
  При 901/911 отложенное редактирование прекращается; для косметического
  закрытия оценки максимум 8 неудачных попыток с растущей задержкой 120–900 с.
  Если VK не даёт изменить карточку, её старые кнопки могут остаться видимыми,
  но сервер уже не принимает оценку по закрытому prompt.
- Обычная отправка и косметическая обработка разделены: 8 отправителей (как
  раньше) и отдельные 2 потока для редактирования/удаления. Координатор не ждёт
  всей пачки: освободившийся слот используется независимо от других запросов.
  Берётся не больше записей, чем есть свободных слотов. Приоритет сообщений
  и проверки устаревших заявок сохранены.
- Активная отправка исключается из выборки редактирования/удаления. Медленная
  отправка не перезахватывается по 30-секундному возрасту в том же процессе.
  При запуске восстанавливаются sending/finalizing/deleting.
- vk_api 11.9.9 не поддерживает аргумент timeout у VkApi. Используется его
  официальный аргумент session с requests.Session: connect 5 с, read 15 с.
  Long Poll имеет свой штатный read timeout 35 с; цикл проверяет прогресс
  запросов даже при отсутствии пользовательских сообщений.
- Firebase HTTP timeout 15 с; UnregisteredError отключает только устаревший
  токен. Обычная сетевая ошибка устройство не отключает. Новый токен можно
  зарегистрировать повторной привязкой приложения.
- Watchdog бота контролирует запуск (180 с), работающие event/timer/outbox
  задачи (180 с), прогресс Long Poll и координатора исходящих (90 с).
  Проверки раз в 5 с; перед восстановлением даётся ещё 10 с на прогресс.
  Пишутся стеки потоков, процесс завершается кодом 70, затем Docker
  restart: unless-stopped запускает контейнер. Это не перезапуск по расписанию.
- Только контейнеру bot заданы SQL statement timeout 30 с, lock timeout 5 с,
  idle-in-transaction timeout 60 с. Миграции и настройки admin не меняются.
- После Alembic бот восстанавливает временные метки консольного журнала.

## Что не менялось

Обработчики и клавиатуры, FIFO и места водителей по линиям, назначение заявок,
параллельные маршруты, отмены, бронирования, цены, комиссии, таймауты принятия,
веб-админка и Android-исходники не изменены. Новых миграций нет.
Часть старых тестов обновлена только для проверки тега v179; одна статическая
проверка вызова finalization обновлена под ограниченную выборку по слотам.
CI теперь устанавливает pinned requirements, чтобы запускать real-ORM тесты.

## Границы гарантий

Это защита от конкретных ошибок и механизм восстановления, а не гарантия
нулевого простоя. Восстановление после зависания занимает время; остаются
отказы VK/Firebase, сети, PostgreSQL и хостинга. Не следует обещать ни
измеренную скорость на сервере, ни exactly-once для всех внешних действий.
При повторной доставке сохраняются random_id и существующие проверки
актуальности. Аварийное завершение откатывает незавершённые транзакции;
фактическую обработку заявок около сбоя нужно проверять по журналу и БД.
Периодически перезапускать исправный бот не требуется.
